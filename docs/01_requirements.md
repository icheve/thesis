# 1. Постановка задачи и требований

---

## 1.1. Определение цели и границ системы

### Бизнес-контекст

Платёжные операции в современных финансовых системах генерируют непрерывный поток событий: инициация платежа, авторизация, клиринг, возврат, отмена. Эти события должны быть доступны аналитическим системам, системам мониторинга и антифрода в режиме близком к реальному времени (NRT — Near Real-Time), а не с задержкой в часы, характерной для классических ночных batch-загрузок.

### Цель системы

Разработать **NRT-конвейер данных**, который:
- принимает события о платежах из одного или нескольких источников,
- обрабатывает и нормализует их,
- поставляет результат потребителям с задержкой **не более 30 секунд** от момента возникновения события,
- сохраняет **полную историю изменений** каждого платежа для аудита и аналитики.

### Границы системы

| Что входит в систему | Что НЕ входит в систему |
|---|---|
| Приём событий от источников (Kafka/CDC) | Исходные транзакционные системы-источники |
| Потоковая обработка и трансформация событий | Фронтенд-интерфейсы для конечных пользователей |
| Хранение текущего состояния и истории платежей | Бизнес-логика принятия решений (антифрод-алгоритмы) |
| Поставка данных потребителям (Kafka topic / table) | Биллинг и расчёты между контрагентами |
| Мониторинг и алерты на уровне конвейера | Эксплуатация инфраструктуры источников |

### Ключевые участники и сценарии

| Участник | Сценарий использования |
|---|---|
| Аналитическая система (BI) | Запрашивает текущее состояние платежей и историю изменений за период |
| Антифрод-система | Потребляет поток событий в режиме реального времени для скоринга |
| Система отчётности | Строит регуляторные отчёты на основе исторических данных |
| Команда эксплуатации | Отслеживает задержки, ошибки и лаг конвейера через dashboard |
| Аудит | Восстанавливает состояние любого платежа на произвольный момент времени |

### Контекстная диаграмма (C4 Context)

```
┌─────────────────────────────────────────────────────────────┐
│                     NRT Payment Pipeline                     │
│                                                             │
│  [Источники] ──► [Ingestion] ──► [Processing] ──► [Sink]   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
       ▲                                        │
       │                                        ▼
  Платёжная БД /                      BI / Антифрод /
  Процессинговая шина                 Отчётность / Аудит
```

**Источники данных (вне системы):**
- Транзакционная СУБД процессингового центра (PostgreSQL / Oracle)
- Очередь событий существующей платёжной шины (Kafka / MQ)

**Потребители данных (вне системы):**
- Аналитическое DWH / BI-платформа
- Антифрод Real-Time Scoring Engine
- Система регуляторной отчётности

## 1.2. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система должна принимать платёжные события из внешних источников (CDC от БД или Kafka-топик) |
| FR-02 | Каждое событие должно быть провалидировано по схеме перед дальнейшей обработкой |
| FR-03 | Система должна нормализовать суммы транзакций к единой базовой валюте (RUB) |
| FR-04 | Система должна нормализовать статусы платежей к единому внутреннему справочнику |
| FR-05 | Система должна поставлять обработанные события потребителям с задержкой NRT (SLA: p99 ≤ 30 с) |
| FR-06 | Система должна сохранять историю всех изменений состояния каждого платежа |
| FR-07 | Система должна поддерживать point-in-time запросы: получение состояния платежа на любой момент времени |
| FR-08 | Обработка дублирующегося события не должна создавать дублирующуюся запись в истории |
| FR-09 | Невалидные и необработанные события должны направляться в Dead Letter Queue (DLQ) |
| FR-10 | Система должна предоставлять метрики задержки и пропускной способности |

## 1.3. Нефункциональные требования

### Производительность и задержка

| Параметр | Целевое значение | Обоснование |
|---|---|---|
| End-to-end latency p50 | ≤ 5 с | Комфортный режим для real-time dashboards |
| End-to-end latency p99 | ≤ 30 с | SLA для NRT-поставки |
| Пиковый throughput | ≥ 1 000 событий/сек | Оценка пиковой нагрузки платёжной системы |
| Baseline throughput | ~200 событий/сек | Среднесуточная нагрузка |

### Надёжность и устойчивость

| Параметр | Требование |
|---|---|
| Гарантия доставки | At-least-once (с идемпотентной записью на стороне sink) |
| Допустимое время недоступности | RTO ≤ 5 мин, RPO = 0 (replay из брокера) |
| Обработка late arrivals | Поддержка событий с опозданием до 10 минут |
| Retry-политика | Экспоненциальный backoff, max 5 попыток перед DLQ |

### Идемпотентность и корректность

| Требование | Описание |
|---|---|
| Идемпотентность записи | Повторная обработка одного события не создаёт дополнительных версий в истории |
| Дедупликация | На уровне брокера (message key) и на уровне sink (уникальный ключ события) |
| Целостность истории | Порядок версий в истории соответствует хронологическому порядку событий |

### Хранение

| Параметр | Требование |
|---|---|
| Срок хранения истории | Не менее 3 лет (регуляторное требование) |
| Партиционирование | По дате события для эффективных range-запросов |
| Объём (оценка) | ~500 МБ/сутки → ~180 ГБ/год при baseline-нагрузке |

### Безопасность

| Требование | Описание |
|---|---|
| Маскирование PII | Поля card_number, account_number хранятся в хешированном/токенизированном виде |
| Шифрование в транзите | TLS для всех соединений между компонентами |
| Шифрование в покое | Шифрование на уровне хранилища |
| Контроль доступа | RBAC: разграничение прав на чтение/запись по ролям (analyst, pipeline, admin) |
| Аудит доступа | Логирование всех обращений к данным платёжной истории |

### Масштабируемость

| Требование | Описание |
|---|---|
| Горизонтальное масштабирование | Добавление экземпляров processing-компонента без остановки конвейера |
| Линейный рост производительности | Увеличение throughput пропорционально числу партиций и экземпляров |
