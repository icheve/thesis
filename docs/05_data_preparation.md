## 5.1. Генератор синтетических платёжных событий

### Назначение

Генератор создаёт синтетический поток событий, максимально приближенный к реальному:
- Реалистичное распределение сумм, статусов, источников и временны́х паттернов
- Управляемая скорость для нагрузочных тестов (baseline / peak / spike)
- Детерминированный режим для воспроизводимых тест-кейсов (seed)
- Специальные режимы: дубли, опоздавшие события, невалидные записи

### Структура генератора

```
generator/
├── payment_generator.py      ← основной генератор событий
├── profiles.py               ← профили нагрузки (baseline/peak/spike)
├── scenarios.py              ← специальные тест-кейсы (дубли, late arrivals, …)
├── schema_registry_client.py ← регистрация Avro-схем
├── kafka_producer.py         ← отправка в Kafka
├── config.py                 ← конфигурация (topic, bootstrap servers, …)
└── requirements.txt          ← зависимости
```

## 5.2. Тестовые кейсы

Тест-кейсы разделены на три группы: **корректность**, **устойчивость** и **нагрузка**.

---

### Группа A — Корректность

#### TC-A01: Базовый жизненный цикл платежа

**Цель:** Проверить, что конвейер корректно обрабатывает нормальную последовательность событий и строит правильную историю.

**Входные данные:**
```
payment_id: PAY-TC-001
Events (в порядке поступления):
  1. CREATED     ts=10:00:00  amount=1500 RUB
  2. AUTHORIZED  ts=10:00:03  amount=1500 RUB
  3. CLEARED     ts=10:05:00  amount=1500 RUB
```

**Ожидаемый результат в `payment_history`:**
```
version=1  CREATED     effective_from=10:00:00  effective_to=10:00:03
version=2  AUTHORIZED  effective_from=10:00:03  effective_to=10:05:00
version=3  CLEARED     effective_from=10:05:00  effective_to=NULL
```

**Ожидаемый результат в `payment_current`:**
```
version=3  status=COMPLETED  amount_rub=1500
```

**Проверки:**
- [ ] `payment_history` содержит ровно 3 строки для `PAY-TC-001`
- [ ] `effective_to` версии N = `effective_from` версии N+1
- [ ] Последняя версия имеет `effective_to = NULL`
- [ ] `payment_current` содержит ровно 1 строку с `version=3`
- [ ] `amount_rub` рассчитан корректно (для RUB = исходная сумма)

---

#### TC-A02: Нормализация суммы и конвертация валюты

**Цель:** Проверить корректность конвертации суммы в RUB по справочному курсу.

**Входные данные:**
```
payment_id: PAY-TC-002
Events:
  1. CREATED  ts=10:00:00  amount=100.00  currency=USD
  2. CLEARED  ts=10:01:00  amount=100.00  currency=USD
```

**Конфигурация справочника:** `USD → RUB = 90.50`

**Ожидаемый результат:**
```
amount_rub = 9050.00
exchange_rate = 90.5000
currency_original = USD
amount_original = 100.0000
```

**Проверки:**
- [ ] `amount_rub = amount_original × exchange_rate` с точностью до 4 знаков
- [ ] `currency_original` сохранена без изменений
- [ ] `exchange_rate` записан тот, что действовал на момент `event_ts`

---

#### TC-A03: Нормализация статуса

**Цель:** Проверить, что статусы разных источников маппятся корректно на внутренний справочник.

**Входные данные:**

| source_system | status (входящий) | status_normalized (ожидаемый) |
|---|---|---|
| ACQUIRING | `AUTH_OK` | `AUTHORIZED` |
| ACQUIRING | `SETTLED` | `COMPLETED` |
| MOBILE_APP | `processing` | `PENDING` |
| MOBILE_APP | `done` | `COMPLETED` |
| INTERNET_BANKING | `REVERSED` | `REFUNDED` |

**Проверки:**
- [ ] Для каждой пары `(source_system, raw_status)` → `status_normalized` соответствует справочнику
- [ ] Неизвестный статус → событие уходит в DLQ с `error_code=E003`

---

#### TC-A04: Обогащение данными мерчанта

**Цель:** Проверить, что `merchant_name` и `merchant_category` заполняются из справочника.

**Входные данные:**
```
merchant_id: MCH-500
Справочник: MCH-500 → {name: "Пятёрочка", category: "GROCERY"}
```

**Ожидаемый результат:**
```
merchant_name = "Пятёрочка"
merchant_category = "GROCERY"
```

**Проверки:**
- [ ] Поля заполнены для всех записей с известным `merchant_id`
- [ ] При `merchant_id = null` → `merchant_name = null`, событие не идёт в DLQ
- [ ] При неизвестном `merchant_id` → поля остаются `null`, событие обрабатывается (не DLQ)

---

### Группа B — Устойчивость к аномалиям

#### TC-B01: Идемпотентность — повторная подача одного события

**Цель:** Убедиться, что дублирующееся eventos не создаёт лишних версий в истории.

**Сценарий:**
1. Отправить событие E1 (`event_id=UUID-1`, `payment_id=PAY-TC-010`, `CREATED`)
2. Подождать обработки
3. Отправить то же событие E1 повторно (идентичный `event_id=UUID-1`)
4. Подождать обработки

**Ожидаемый результат:**
- `payment_history` для `PAY-TC-010` содержит ровно **1 строку** (не 2)
- Метрика `flink_events_processed_total` = 2 (оба события прочитаны)
- Второе событие помечено `is_duplicate=true` в `payments.processed`

**Проверки:**
- [ ] `SELECT count() FROM payment_history WHERE payment_id='PAY-TC-010'` = `1`
- [ ] В логах Flink: `"is_duplicate": true` для второго события

---

#### TC-B02: Out-of-order события

**Цель:** Проверить, что история корректно строится при нарушении порядка поступления событий.

**Сценарий (порядок поступления в Kafka ≠ порядку по event_ts):**
```
Поступили в Kafka:
  t=0 с:   event AUTHORIZED  (event_ts=10:00:03)
  t=1 с:   event CREATED     (event_ts=10:00:00)  ← опоздало на 1 с
  t=2 с:   event CLEARED     (event_ts=10:05:00)
```

**Ожидаемый результат в `payment_history`:**
```
version=1  CREATED     effective_from=10:00:00  effective_to=10:00:03
version=2  AUTHORIZED  effective_from=10:00:03  effective_to=10:05:00
version=3  CLEARED     effective_from=10:05:00  effective_to=NULL
```
Порядок версий должен соответствовать `event_ts`, а не порядку поступления в Kafka.

**Проверки:**
- [ ] История отсортирована по `effective_from ASC` в правильном хронологическом порядке
- [ ] `version` монотонно возрастает в порядке `event_ts`

---

#### TC-B03: Late Arrival (событие с опозданием > watermark)

**Цель:** Проверить обработку события, опоздавшего за пределы watermark (> 10 минут).

**Сценарий:**
```
12:00:00  CREATED    поступило и обработано
12:00:05  AUTHORIZED поступило и обработано
12:15:00  CLEARED    поступило и обработано
12:20:00  Flink watermark = 12:10:00 (current_max - 10 min)

Затем поступает событие:
  event_ts = 11:55:00  status = PRE_AUTH  ← опоздало на 25 минут
```

**Ожидаемый результат:**
- Событие направлено в side output `payments.late`, НЕ в `payments.raw` основной обработки
- Логируется с тегом `late_arrival=true`
- `payment_history` основного потока не нарушена
- Оператор может вручную инициировать replay опоздавшего события

**Проверки:**
- [ ] `payments.late` содержит сообщение с `event_ts=11:55:00`
- [ ] `payment_history` НЕ содержит строку с `event_ts=11:55:00`
- [ ] Алерт `late_arrival_count > 0` срабатывает в Grafana

---

#### TC-B04: Невалидное событие → DLQ

**Цель:** Убедиться, что невалидные события корректно перехватываются и не попадают в хранилище.

**Сценарии:**

| Кейс | Входные данные | Ожидаемый error_code |
|---|---|---|
| B04-a | `payment_id = null` | E002 |
| B04-b | `currency = "XXX"` (неизвестная) | E003 |
| B04-c | `amount = "abc"` (не число) | E001 |
| B04-d | `source_system = "UNKNOWN_SYS"` | E004 |
| B04-e | Поле `event_type` отсутствует в Avro | E001 |

**Проверки:**
- [ ] Событие NOT IN `payment_history` и NOT IN `payment_current`
- [ ] `payments.dlq` содержит сообщение с корректным `error_code`
- [ ] `flink_validation_errors_total` инкрементировалось
- [ ] `original_payload_b64` в DLQ декодируется в исходное сообщение

---

#### TC-B05: Schema Evolution — новая версия схемы

**Цель:** Проверить, что конвейер продолжает работу при добавлении нового nullable-поля в схему.

**Сценарий:**
1. Зарегистрировать схему v1 (без поля `channel`)
2. Отправить и обработать 100 событий по схеме v1
3. Зарегистрировать схему v2 (добавлено `channel: nullable string, default null`)
4. Отправить 100 событий по схеме v2 (с заполненным `channel`)
5. Отправить 50 событий по схеме v1 (старые продюсеры)

**Ожидаемый результат:**
- Все 250 событий обработаны без ошибок
- Для событий v1: `channel = null`
- Для событий v2: `channel` заполнен

**Проверки:**
- [ ] Нет роста `flink_validation_errors_total` при смешанных схемах
- [ ] Schema Registry содержит обе версии

---

#### TC-B06: Падение Flink и восстановление из checkpoint

**Цель:** Убедиться, что после перезапуска Flink не теряет события и не создаёт дублей.

**Сценарий:**
1. Запустить поток событий (200 событий/сек)
2. После 30 секунд — принудительно завершить Flink job (kill -9 taskmanager)
3. Flink автоматически рестартует из последнего checkpoint
4. Продолжить поток событий
5. Через 60 секунд — проверить полноту данных

**Ожидаемый результат:**
- Нет пропущенных событий (сравнить count в Kafka с count в ClickHouse)
- Нет дублей (count в `payment_history FINAL` = уникальных событий)
- Задержка восстановления ≤ 2 минут

**Проверки:**
- [ ] `kafka offset` consumed = `clickhouse count(DISTINCT event_id)`
- [ ] `SELECT count() - uniqExact(event_id) FROM payment_history` = `0`
- [ ] Время до полного восстановления лага ≤ 120 с

---

#### TC-B07: Недоступность ClickHouse — буферизация и повтор

**Цель:** Проверить поведение конвейера при временной недоступности sink.

**Сценарий:**
1. Запустить поток (200 событий/сек)
2. Остановить ClickHouse на 3 минуты
3. Запустить ClickHouse снова
4. Подождать восстановления

**Ожидаемый результат:**
- Flink продолжает читать из Kafka (consumer lag растёт)
- Retry-запросы к ClickHouse с экспоненциальным backoff
- После восстановления ClickHouse — все буферизованные события записаны
- Итоговый `payment_history` содержит все события без пропусков

**Проверки:**
- [ ] В период недоступности: `clickhouse_insert_errors_total` > 0
- [ ] После восстановления: consumer lag вернулся к 0 в течение 5 мин
- [ ] Нет потери данных: count в Kafka == count в ClickHouse

---

### Группа C — Нагрузка

#### TC-C01: Baseline нагрузка (200 событий/сек, 30 минут)

**Цель:** Убедиться в стабильной работе при нормальной нагрузке.

**Параметры:**
```
Rate:     200 events/sec
Duration: 30 min
Total:    ~360 000 events
```

**Критерии успеха:**
- [ ] p50 latency ≤ 5 с
- [ ] p99 latency ≤ 30 с
- [ ] Error rate < 0.1%
- [ ] Consumer lag ≤ 1 000 сообщений

---

#### TC-C02: Peak нагрузка (1 000 событий/сек, 10 минут)

**Цель:** Проверить поведение системы на пиковой нагрузке.

**Параметры:**
```
Rate:     1 000 events/sec
Duration: 10 min
Total:    ~600 000 events
```

**Критерии успеха:**
- [ ] p99 latency ≤ 30 с (SLA не нарушается даже на пике)
- [ ] Error rate < 0.5%
- [ ] Consumer lag возвращается к 0 в течение 5 мин после окончания пика
- [ ] Нет OOM в Flink TaskManagers

---

#### TC-C03: Spike нагрузка (10× burst, 1 минута)

**Цель:** Проверить эластичность при резком кратковременном всплеске.

**Сценарий:**
```
0–5 мин:   200 events/sec  (baseline)
5–6 мин:   2 000 events/sec (10× spike)
6–15 мин:  200 events/sec  (возврат к baseline)
```

**Критерии успеха:**
- [ ] В период spike: consumer lag растёт, но не более 120 000 сообщений
- [ ] p99 latency в период spike может превышать SLA (до 120 с) — допустимо
- [ ] После spike: lag рассасывается в течение 10 мин
- [ ] Нет потери данных и нет дублей
