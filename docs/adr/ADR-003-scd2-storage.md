# ADR-003: Стратегия хранения истории — SCD Type 2 + Append-Only Log

| Поле | Значение |
|------|---------|
| **Дата** | 2026-01-25 |
| **Статус** | Принято |
| **Авторы** | Команда проекта |

## Контекст

Необходимо хранить полную историю изменений платежей для аналитики (требование FR-04). Рассматриваются несколько паттернов хранения исторических данных в ClickHouse.

## Рассматриваемые варианты

### SCD Type 1 (overwrite)

Хранится только текущее состояние. История уничтожается при каждом обновлении.

**Минусы:** невозможно ответить на вопрос «каким был статус платежа в момент T?».  
**Вывод:** не подходит — нарушает FR-04.

### SCD Type 2 (versioned rows в одной таблице)

Каждое изменение создаёт новую строку с полями `effective_from`, `effective_to`, `is_current`.

**Плюсы:** полная история, простые запросы «состояние на момент T».  
**Минусы:** в ClickHouse нет нативного UPSERT — обновление `effective_to` предыдущей строки невозможно атомарно.

### Append-Only Event Log

Каждое событие просто добавляется. Нет полей `effective_to`.

**Плюсы:** идеально подходит ClickHouse (INSERT-only).  
**Минусы:** запросы «текущее состояние» и «состояние на момент T» требуют сложных оконных функций.

### Гибридная модель: две таблицы

- `payment_current` (`ReplacingMergeTree`) — «витрина» текущего состояния
- `payment_history` (append-only MergeTree) — полный лог версий в стиле SCD Type 2

**Плюсы:**
- `payment_current` быстро отвечает на «что сейчас»
- `payment_history` хранит все версии без необходимости UPDATE
- Каждая таблица оптимизирована под свой паттерн доступа

**Минусы:**
- Нужно поддерживать консистентность двух таблиц
- Дублирование последней версии в обоих таблицах

## Решение

**Выбрана гибридная модель (две таблицы).**

### `payment_current` (ReplacingMergeTree по version)

- Хранит только последнюю версию каждого платежа
- Дедупликация осуществляется ClickHouse при слиянии (OPTIMIZE) или через `FINAL` в запросах
- INSERT новой версии «вытесняет» старую без явного UPDATE

### `payment_history` (MergeTree, append-only)

- Каждая строка — неизменяемая версия платежа
- `effective_from` = время начала версии, `effective_to` = время начала следующей версии
- `is_current = 0` для закрытых версий, `is_current = 1` для открытой
- Закрытие предыдущей версии происходит в Flink (`ScdMergerOperator`) перед записью новой — не в ClickHouse

Ключевое свойство: **ClickHouse никогда не делает UPDATE** — только INSERT. Это соответствует колоночной природе хранилища и обеспечивает максимальную производительность записи.

## Последствия

- При запросе «текущее состояние» используется `payment_current FINAL` (дешевле, чем оконные функции по `payment_history`)
- При запросе «состояние на момент T» используется `payment_history WHERE effective_from ≤ T AND effective_to > T`
- Консистентность двух таблиц гарантируется Flink: обе таблицы пишутся в одном `ClickHouseSink` в рамках одного батча; при сбое checkpoint гарантирует повтор обеих записей (idempotency обеспечивает ReplacingMergeTree)
- DQ-тест TC-DQ-026 проверяет консистентность таблиц в рамках регрессии
