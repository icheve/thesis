# ADR-004: Стратегия дедупликации — трёхуровневый подход

| Поле | Значение |
|------|---------|
| **Дата** | 2026-02-01 |
| **Статус** | Принято |
| **Авторы** | Команда проекта |

## Контекст

При at-least-once доставке возможны дублирующиеся события в Kafka. Необходимо гарантировать, что дублирование не приводит к лишним строкам в ClickHouse.

Дублирование может возникать на нескольких уровнях:
1. **Источник** отправляет одно событие дважды (retry приложения)
2. **Flink** перезапускается из checkpoint и переобрабатывает последние события
3. **ClickHouse sink** ретраит неудавшийся INSERT и вставляет одни данные дважды

## Варианты

### Одноуровневая дедупликация (только ClickHouse)

ReplacingMergeTree дедупликирует при слиянии, но:
- Слияние происходит асинхронно → временные дубли видны в запросах
- `FINAL` modifier или `OPTIMIZE TABLE` медленнее при высоком RPS вставок

### Двухуровневая (Flink state + ClickHouse)

Flink хранит `MapState[event_id → ts]` и отбрасывает повторы. ClickHouse дублирует для защиты от ретрая sink.

Проблема: при разных `event_id` с одинаковым содержанием (ретрай источника с новым ID) дедупликация не срабатывает.

### Трёхуровневая (идемпотентный producer + Flink state + ClickHouse + контентный хэш)

Описание каждого уровня:

| Уровень | Механизм | Что дедуплицирует |
|---------|----------|------------------|
| L1 | Kafka idempotent producer | Повторную отправку одного producer'а в пределах сессии |
| L2 | Flink `MapState[event_id]` (TTL 24h) | Повторы по `event_id` при перезапуске из checkpoint |
| L3a | ClickHouse `payment_current` `ReplacingMergeTree(version)` + `payment_history` `ReplacingMergeTree(processed_at)` | Повторный INSERT той же версии через sink retry |
| L3b | Flink content hash (`_compute_field_hash`) | Разные `event_id`, но одинаковые значимые поля |

## Решение

**Принята трёхуровневая стратегия.**

Уровень L3b (контентный хэш) является ключевым нефункциональным требованием: источник может генерировать события с разными `event_id` при повторе (например, при таймауте HTTP-вызова). Хэш вычисляется по полям: `payment_id`, `status_normalized`, `event_type`, `amount_rub`, `merchant_id`, `currency_original`.

### TTL для Flink MapState

TTL = 24 часа — баланс между:
- Памятью RocksDB (при 200 событий/сек за 24ч = 17.3 M записей × ~50 байт = ~865 MB)
- Вероятностью повторной доставки старых событий (крайне мала для > 24h)

## Последствия

- При replay из Kafka (для исправления данных) MapState очищена, поэтому события за прошедшие > 24h могут дублированно обрабатываться. Защита: ClickHouse ReplacingMergeTree + консистентный `version`.
- L3b hash означает: если источник изменит незначимое поле (например, metadata), новая версия **не** создаётся. Список значимых полей зафиксирован в `ScdMergerOperator._compute_field_hash()` и задокументирован.
