# ADR-001: Выбор архитектурного паттерна — Kappa vs Lambda

| Поле | Значение |
|------|---------|
| **Дата** | 2026-01-15 |
| **Статус** | Принято |
| **Авторы** | Команда проекта |

## Контекст

Необходимо выбрать архитектурный паттерн для системы доставки платёжных данных в NRT-режиме. Два основных кандидата: Lambda-архитектура (два параллельных пути: batch + streaming) и Kappa-архитектура (единственный потоковый путь).

## Рассматриваемые варианты

### Lambda-архитектура

**Плюсы:**
- Batch-слой обеспечивает «исправление» данных при обнаружении ошибок
- Высокая отказоустойчивость: serving layer может переключаться между batch и speed view
- Зрелые инструменты для batch-обработки (Spark)

**Минусы:**
- Два независимых пути обработки → двойные усилия на разработку и поддержку
- Сложность синхронизации batch и speed слоёв (разные схемы, разные задержки)
- Рассогласование данных между слоями при изменении бизнес-логики
- Высокая операционная сложность для дипломного проекта

### Kappa-архитектура

**Плюсы:**
- Один унифицированный код обработки
- Проще поддерживать и тестировать
- Replay данных из Kafka (retention up to 30 дней) заменяет batch-переработку
- Современные потоковые движки (Flink) поддерживают все нужные паттерны

**Минусы:**
- Replay большого объёма данных из Kafka медленнее полноценного batch
- Требует достаточного retention в Kafka для сценариев исправления данных

## Решение

**Выбрана Kappa-архитектура.**

Мотивация:
1. Объём данных (≤ 200 событий/сек, 30-дневный Kafka retention = ~500 GB) допускает replay без batch-слоя.
2. Late arrivals обрабатываются через watermark + side output (`payments.late`), а не через batch-переработку.
3. Снижение операционной сложности критично для дипломного проекта, где приоритет — корректность реализации, а не производственная зрелость.

## Последствия

- Kafka retention для `payments.raw` установлен в 3 дня (рабочий объём) + возможность увеличения до 30 дней для replay.
- При необходимости исправления исторических данных используется replay: перезапуск Flink-задания с earliest offset.
- Отказ от batch-слоя означает, что исправление данных за период > 30 дней потребует доработки (хранение raw событий в S3/HDFS).
