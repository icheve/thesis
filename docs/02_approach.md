# 2. Обзор и выбор подхода

---

## 2.1. Обзор архитектурных паттернов

### Lambda-архитектура

Lambda-архитектура разделяет обработку данных на два независимых слоя:
- **Batch layer** — периодически (раз в час / раз в сутки) перечитывает все исходные данные и строит «истинные» агрегаты.
- **Speed layer** — обрабатывает события в реальном времени и даёт приближённые результаты до завершения batch-прогона.
- **Serving layer** — объединяет результаты обоих слоёв для запросов.

| Плюсы | Минусы |
|---|---|
| Высокая точность batch-результатов | Двойная кодовая база (одна логика — дважды) |
| Устойчивость к ошибкам в speed layer | Сложность синхронизации двух слоёв |
| Зрелые инструменты для каждого слоя | Высокие операционные затраты |

**Применимость к данной задаче:** Lambda избыточна — нам не нужны независимые batch-агрегаты; история платежей строится на потоке событий без необходимости batch-пересчёта.

---

### Kappa-архитектура

Kappa-архитектура упрощает Lambda: **единственный слой потоковой обработки** работает как для «живого» потока, так и для исторического replay (брокер сообщений хранит лог событий достаточно долго).

```
Источник → [Брокер / Event Log] → [Stream Processor] → [Sink / Хранилище]
                    ▲                                          │
                    └──────── Replay (при необходимости) ──────┘
```

| Плюсы | Минусы |
|---|---|
| Единая кодовая база — одна логика обработки | Брокер должен хранить события достаточно долго для replay |
| Проще эксплуатировать | Replay может быть медленным при больших объёмах |
| Естественно подходит для NRT-пайплайна | Требует stateful-обработки для корректного ведения истории |

**Вывод:** Kappa-архитектура является оптимальным выбором для данной задачи.

---

### Event-driven pipeline vs Batch ETL

| Критерий | Batch ETL | Event-driven NRT pipeline |
|---|---|---|
| Задержка поставки | Часы | Секунды (NRT) |
| Сложность реализации | Низкая | Средняя |
| Обработка late arrivals | Простая (следующий batch) | Требует windowing и watermark |
| Гарантии корректности истории | Высокие (полный пересчёт) | Требует идемпотентности и дедупликации |
| Соответствие требованиям (p99 ≤ 30 с) | **Не соответствует** | **Соответствует** |

**Вывод:** Batch ETL не удовлетворяет требованию NRT — необходим event-driven подход.

---

### CDC (Change Data Capture) как метод ingestion

CDC позволяет захватывать изменения непосредственно из transaction log СУБД (WAL в PostgreSQL, redo log в Oracle) без нагрузки на источник.

**Сравнение методов ingestion:**

| Метод | Задержка | Нагрузка на источник | Полнота данных |
|---|---|---|---|
| Polling (периодический SELECT) | Секунды–минуты | Средняя | Риск пропуска при UPDATE+DELETE |
| Triggers + outbox table | Секунды | Низкая | Высокая, но требует изменений в источнике |
| CDC из WAL (Debezium) | Миллисекунды–секунды | Минимальная | Полная (все операции INSERT/UPDATE/DELETE) |
| Kafka Producer (источник сам пишет) | Миллисекунды | На стороне источника | Зависит от источника |

**Вывод:** CDC через Debezium (или Kafka Producer, если источник управляем) — предпочтительный метод.

---

### Паттерны хранения истории изменений

| Паттерн | Описание | Применимость |
|---|---|---|
| **SCD Type 1** | Перезапись текущего значения | Нет — история не сохраняется |
| **SCD Type 2** | Новая строка при каждом изменении, флаги `effective_from` / `effective_to` + `is_current` | Да — подходит для аналитических запросов |
| **Event Sourcing** | Хранение только событий, состояние вычисляется на лету | Да — идеально для replay, но дорогие read-запросы |
| **Append-only log + снапшоты** | Лог событий + периодические снапшоты текущего состояния | Да — баланс между read и write производительностью |
| **Time-travel (Delta Lake / Iceberg)** | Версионирование на уровне таблицы средствами формата | Да — прозрачно для запросов, требует поддерживаемого формата |

**Вывод:** Для данной задачи выбирается **SCD Type 2 + append-only event log**: SCD Type 2 для текущего состояния (быстрые аналитические запросы), event log как источник истины для replay и аудита.

## 2.2. Обзор инструментов

### Брокеры сообщений

| Критерий | Apache Kafka | Apache Pulsar | RabbitMQ |
|---|---|---|---|
| Задержка (p99) | 5–15 мс | 5–15 мс | 1–5 мс |
| Retention событий | Дни / недели (настраиваемо) | Дни / недели (tiered storage) | Минуты–часы (без плагинов) |
| Масштабируемость | Очень высокая (партиции) | Очень высокая (topic разбить проще) | Средняя |
| Replay событий | Нативно (offset reset) | Нативно | Ограниченно |
| Экосистема | Огромная (Kafka Connect, Streams, Schema Registry) | Активная, но меньше | Умеренная |
| Зрелость | Очень высокая | Высокая | Очень высокая |
| Сложность эксплуатации | Средняя (ZooKeeper → KRaft) | Средняя (BookKeeper) | Низкая |

**Вывод:** Apache Kafka — стандарт де-факто для NRT-пайплайнов с требованием replay и высокой пропускной способностью.

---

### Потоковая обработка

| Критерий | Apache Flink | Spark Structured Streaming | Kafka Streams |
|---|---|---|---|
| Модель обработки | Native streaming (событие за событием) | Micro-batch (по умолчанию) | Native streaming |
| Задержка | Миллисекунды | Секунды (batch interval) | Миллисекунды |
| Stateful processing | Нативно, масштабируемо | Поддерживается | Поддерживается (ограниченно) |
| Exactly-once | Да (checkpointing) | Да | Да (transactions) |
| Late arrivals / Watermark | Нативная поддержка | Поддерживается | Ограниченно |
| Масштабируемость | Очень высокая | Высокая | Средняя (ограничена числом партиций) |
| Операционная сложность | Высокая (кластер Flink) | Средняя (поверх Spark) | Низкая (library, без кластера) |
| Применимость | Enterprise NRT | Batch + NRT hybrid | Простые pipeline в рамках Kafka |

**Вывод:** Apache Flink — наилучший выбор для NRT с sub-second latency, нативным watermark и масштабируемым stateful-processing.

---

### Хранилища данных

| Критерий | ClickHouse | Apache Iceberg (+ S3/HDFS) | PostgreSQL (партиционированный) |
|---|---|---|---|
| Тип | Колоночная OLAP СУБД | Открытый табличный формат | Строчная OLTP/OLAP СУБД |
| Скорость аналитических запросов | Очень высокая | Высокая (зависит от движка) | Удовлетворительная |
| Поддержка history / SCD | Ручная реализация | Time-travel нативно | Ручная реализация |
| Upsert / Merge | ReplacingMergeTree / CollapsingMergeTree | MERGE INTO (Apache Iceberg + Flink) | Нативный UPSERT |
| Партиционирование | Нативное (PARTITION BY) | Нативное | Нативное |
| Масштабируемость | Горизонтальная (шардирование) | Горизонтальная (object storage) | Вертикальная / ограниченная |
| Retention / Archiving | TTL на уровне таблицы | S3 lifecycle policies | Tablespace / pg_partman |
| Операционная сложность | Средняя | Высокая (требует compute engine) | Низкая |

**Вывод:** ClickHouse — оптимальный выбор: высокая скорость аналитических запросов, нативный TTL для retention, реализация SCD через `ReplacingMergeTree`, низкая операционная сложность по сравнению с Iceberg.

### Ограничения и компромиссы принятого решения

| Ограничение | Принятый компромисс |
|---|---|
| Flink требует отдельного кластера | В dev-среде используется Flink в режиме `local` (embedded), в prod — standalone mini-cluster |
| ClickHouse не поддерживает транзакционный UPSERT в классическом смысле | Используется `ReplacingMergeTree` с дедупликацией по версии; финальная дедупликация через `FINAL` или `optimize_on_insert` |
| Schema Registry — дополнительный компонент | Принято за необходимость для обеспечения schema evolution и совместимости |
| Exactly-once в Flink → ClickHouse требует двухфазной фиксации | Используется at-least-once + идемпотентная запись (ReplacingMergeTree) как практически эквивалентная гарантия |
