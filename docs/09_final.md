# Шаг 9. Итоговая документация и выводы

## 9.1 Аннотация проекта

В рамках выпускной квалификационной работы разработана система доставки платёжных данных в режиме, близком к реальному времени (Near Real-Time, NRT), с сохранением полной истории изменений на основе паттерна Slowly Changing Dimension Type 2 (SCD2).

**Задача:** обеспечить доставку событий об изменении статуса платежей из OLTP-систем в аналитическое хранилище с задержкой не более 30 секунд (p99) при сохранении полной версионной истории и effectively-exactly-once семантикой обработки на уровне аналитического состояния.

---

## 9.2 Архитектурные решения и их обоснование

### Выбранный стек

| Компонент | Решение | Альтернативы | Причина выбора |
|-----------|---------|-------------|----------------|
| Брокер сообщений | Apache Kafka 3.x | RabbitMQ, Apache Pulsar | Наивысшая пропускная способность, компактный лог, нативная поддержка replay |
| Потоковая обработка | Apache Flink 1.19 | Spark Structured Streaming, Kafka Streams | Stateful KeyedProcessFunction, точное управление временем, RocksDB state backend |
| Аналитическое хранилище | ClickHouse 24.x | Apache Iceberg, PostgreSQL | Векторизованное выполнение, реальная производительность аналитических запросов |
| Схемы | JSON + SimpleStringSchema (прототип) | Avro + Schema Registry — production-расширение | Schema evolution, BACKWARD-совместимость |
| Мониторинг | Prometheus + Grafana | Datadog, InfluxDB | OpenSource, нативная интеграция с Flink JMX |

### Паттерн архитектуры

Выбрана **Kappa-архитектура** (единый потоковый путь), а не Lambda (batch + streaming), поскольку:
- Все аналитические запросы могут обслуживаться из одного источника (ClickHouse)
- Нет необходимости в batch-уровне: для replay достаточно Kafka retention. Late arrivals предусмотрены watermark + side output, но маршрутизация в `payments.late` отключена в прототипе (Beam PyFlink runtime не поддерживает `ctx.timer_service()`); все события обрабатываются в основном потоке (допустимо для прототипа)
- Снижается операционная сложность: один runtime вместо двух

### Гарантия однократной обработки

Ни один из компонентов стека не обеспечивает exactly-once сквозь всю цепочку «из коробки». Реализована **композитная стратегия**:

```
Kafka (at-least-once, idempotent producer)
  → Flink (at-least-once checkpoint; state консистентен относительно checkpoint)
    → 3-уровневая дедупликация:
        L1: Kafka idempotent producer (по ключу + sequence)
        L2: Flink MapState[event_id → ts] (TTL 24h)
        L3: ClickHouse ReplacingMergeTree(version) + контентный хэш
```

Итог: **effectively-exactly-once** — событие может поступить несколько раз, но в хранилище появится ровно одна запись.

### 9.3.2 Нагрузочный тест TC-C01 (базовая нагрузка, 200 событий/сек)

| Метрика | Значение | SLA | Результат |
|---------|----------|-----|-----------|
| e2e latency p50 | 5.5 с ¹ | — | — |
| e2e latency p99 | **6.0 с ¹** | ≤ 30 с | ✅ |
| Consumer lag (max) | 0 сообщений | — | — |

| Flink checkpoint duration | 0.62 с | < 30 с | ✅ |

¹ *Метрика `pipeline_e2e_latency_seconds` является gauge-derived approximation: фиксирует время от event_ts источника до момента обработки в ScdMergerOperator (до ClickHouse sink). Истинные end-to-end перцентили требуют перехода с gauge на histogram или post-hoc ClickHouse quantile. SLA выполнен.*

**Вывод:** при целевой нагрузке 200 событий/сек система обеспечивает SLA p99 ≤ 30 с (6.0 с по gauge-метрике). Эффективная ёмкость стенда (1 TaskManager, 4 слота) — **~480 событий/сек**.

## 9.5 Ограничения реализации

1. **Однонодовый Kafka:** в dev-окружении Kafka работает на одном broker'е без репликации. В production необходим кластер из ≥ 3 брокеров с `replication.factor=3`.

2. **Avro не реализован, используется JSON:** пайплайн читает из Kafka через `SimpleStringSchema` (JSON). Schema Registry поднят как инфраструктурный сервис (docker compose), но пайплайн его не использует. Avro + Schema Registry — production-расширение. Следствие: нет автоматической schema evolution и контроля совместимости. В production необходим переход на Avro + Schema Registry с настроенной BACKWARD-совместимостью и аутентификацией (mTLS / Basic Auth).

3. **ClickHouse без шардирования:** один узел ClickHouse. При нагрузке > 5 000 событий/сек потребуется ClickHouse Cluster с Distributed таблицами.

4. **Watermark = 10 минут / Маршрутизация late arrivals отключена:** в текущей реализации side output через `ctx.timer_service()` не поддерживается в Beam PyFlink 1.19 runtime. Все события, включая опоздавшие, обрабатываются в основном потоке. Это приемлемо для прототипа — `effective_from` всё равно заполняется из `event_ts` исходного события, хронология истории корректна. Топик `payments.late` создан, но не заполняется. Для production необходим переход на native Flink Java/Scala или отдельная batch-процедура коррекции.

5. **DLQ пишется только в Kafka, не в ClickHouse:** невалидные события направляются в Kafka-топик `payments.dlq`. Таблица `payment_dlq` в ClickHouse создана DDL-скриптом, но пайплайн её не заполняет. Прямая верификация DLQ через ClickHouse-запрос невозможна; тесты TC-A04, TC-B03, TC-B06 проверяют DLQ косвенно (по отсутствию записи в `payment_current`/`payment_history`), прямая проверка Kafka-топика помечена xfail.

6. **PII-маскирование не реализовано в пайплайне:** конвейер работает с уже токенизированными идентификаторами (`payer_id`, `payee_id` — токены со стороны источника). Дополнительное маскирование на уровне Flink не реализовано в прототипе (TODO в тестах). Для полного соответствия GDPR/152-ФЗ необходима дополнительная анонимизация на стороне источника или в ValidatorOperator.

## 9.7 Заключение

В ходе работы:

1. **Проведён сравнительный анализ** архитектурных паттернов (Lambda vs Kappa) и инструментов обработки потоков, обоснован выбор стека Kafka + Flink + ClickHouse.

2. **Спроектирована архитектура** NRT-пайплайна с гарантией effectively-exactly-once, трёхуровневой дедупликацией и гибридной моделью хранения (SCD Type 2 + append-only лог).

3. **Реализован рабочий прототип** — полностью функциональный код пайплайна (PyFlink DataStream API), генератор тестовых данных, мониторинг и автоматизированные тесты.

4. **Проведено тестирование:** 9/10 FR подтверждены тест-кейсами (TC-B07 late arrivals — xfail, Beam runtime). SLA p99 ≤ 30 с выполнен при нагрузке до **~480 событий/сек** (1 TaskManager); при 1 000 ев/с p99 = 95.79 с — требуется горизонтальное масштабирование. RPO = 0 подтверждён в тесте восстановления.

5. **Рассчитана ёмкость:** ~1.4 ТБ реальных данных за 3 года (с учётом сжатия LZ4).

Разработанная система подтверждает ключевые требования прототипа (9/10 FR, SLA p99 при базовой нагрузке, RPO = 0) и может служить основой для production-развёртывания при устранении указанных ограничений.
