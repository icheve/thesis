# Шаг 9. Итоговая документация и выводы

## 9.1 Аннотация проекта

В рамках выпускной квалификационной работы разработана система доставки платёжных данных в режиме, близком к реальному времени (Near Real-Time, NRT), с сохранением полной истории изменений на основе паттерна Slowly Changing Dimension Type 2 (SCD2).

**Задача:** обеспечить доставку событий об изменении статуса платежей из OLTP-систем в аналитическое хранилище с задержкой не более 30 секунд (p99) при сохранении полной версионной истории и effectively-exactly-once семантикой обработки на уровне аналитического состояния.

**Контекст нагрузки:** целевой параметр 200 событий/сек (baseline) соответствует ~17.3 млн платёжных событий в сутки — типовому объёму аналитического конвейера крупного российского банка или среднего платёжного сервиса. По открытым данным ЦБ РФ (таблица T7, «Статистика НПС»), в 2023–2024 гг. российские банки проводили суммарно ~38–44 млрд операций в год (~1 400 событий/с по всей отрасли). Обоснование целевых уровней нагрузки — см. [docs/01_requirements.md](01_requirements.md), §1.1 «Обоснование целевой нагрузки».

## 9.2 Архитектурные решения и их обоснование

### Выбранный стек

| Компонент | Решение | Альтернативы | Причина выбора |
|-----------|---------|-------------|----------------|
| Брокер сообщений | Apache Kafka 3.x | RabbitMQ, Apache Pulsar | Наивысшая пропускная способность, компактный лог, нативная поддержка replay |
| Потоковая обработка | Apache Flink 1.19 | Spark Structured Streaming, Kafka Streams | Stateful KeyedProcessFunction, точное управление временем, RocksDB state backend |
| Аналитическое хранилище | ClickHouse 24.x | Apache Iceberg, PostgreSQL | Векторизованное выполнение, реальная производительность аналитических запросов |
| Схемы | JSON + SimpleStringSchema (прототип) | Avro + Schema Registry — production-расширение | Schema evolution, BACKWARD-совместимость |
| Мониторинг | Prometheus + Grafana | Datadog, InfluxDB | OpenSource, нативная интеграция с Flink JMX |

### Паттерн архитектуры

Выбрана **Kappa-архитектура** (единый потоковый путь), а не Lambda (batch + streaming), поскольку:
- Все аналитические запросы могут обслуживаться из одного источника (ClickHouse)
- Нет необходимости в batch-уровне: для replay достаточно Kafka retention. Late arrivals предусмотрены watermark + side output, но маршрутизация в `payments.late` отключена в прототипе (Beam PyFlink runtime не поддерживает `ctx.timer_service()`); все события обрабатываются в основном потоке (допустимо для прототипа)
- Снижается операционная сложность: один runtime вместо двух

### Гарантия однократной обработки

Ни один из компонентов стека не обеспечивает exactly-once сквозь всю цепочку «из коробки». Реализована **композитная стратегия**:

```
Kafka (at-least-once, idempotent producer)
  → Flink (at-least-once checkpoint; state консистентен относительно checkpoint)
    → 3-уровневая дедупликация:
        L1: Kafka idempotent producer (по ключу + sequence)
        L2: Flink MapState[event_id → ts] (TTL 24h)
        L3: ClickHouse ReplacingMergeTree(version) + контентный хэш
```

Итог: **effectively-exactly-once** — событие может поступить несколько раз, но в хранилище появится ровно одна запись.

### 9.3.5 Точность SCD Type 2

Корректность SCD Type 2 логики верифицирована функциональными тестами:

- **TC-A02** — переход статуса одного платежа создаёт новую версию в `payment_history` и обновляет `payment_current`; предыдущая версия корректно закрывается (`effective_to` проставлен Flink'ом до записи в ClickHouse).
- **TC-B01** — полный жизненный цикл платежа из 5 статусов на одном `payment_id`; в `payment_history` появляется 5 версий с непрерывной хронологией, в `payment_current FINAL` — ровно одна строка с последним статусом.

DQ-тесты (`test_data_quality.py`) проверяют структурные инварианты на данных нагрузочного прогона:

| Проверка | Результат |
|---------|-----------|
| Уникальность event_id в payment_history | ✅ |
| Единственная открытая версия (is_current=1) на платёж | ✅ |
| Положительные суммы | ✅ |
| Консистентность payment_current и payment_history | ✅ |

> Примечание: нагрузочный тест (`load_test.py`) генерирует уникальный `payment_id` для каждого события, поэтому многоверсионные сценарии покрыты функциональными тестами TC-A02 и TC-B01, а не нагрузочным прогоном. Проверка непрерывности дат (`effective_to = effective_from` следующей версии) подтверждена в рамках TC-B01.

### 9.3.6 Тесты TC-C05/TC-C06/TC-C07 — верификация async ClickHouse sink

**Конфигурация тестов:**

| Тест | TM | parallelism | Нагрузка | Выход | Файл результата |
|------|----|-------------|----------|-------|-----------------|
| TC-C05 | 1 | 4 | 500 ев/с | `load_report_1tm_500.json` | Базовая линия |
| TC-C06 | 2 | 8 | 500 ев/с | `load_report_2tm_500.json` | После async-фикса |
| TC-C07 | 2 | 8 | 900 ев/с | `load_report_2tm_900.json` | Поиск потолка |

**Результаты:**

| Тест | e2e p99, с | events/sec | lag | Checkpoint, мс | SLA |
|------|-----------|-----------|-----|---------------|-----|
| TC-C05 (1 TM, 500 ев/с) | **69.94** | 400 | 3 307 | 13 952 | ❌ |
| TC-C06 (2 TM, 500 ев/с) | **14.0** | 439 | 128 | 14 727 | ✅ |
| TC-C07 (2 TM, 900 ев/с) | 293.44 | 516 | 20 639 | 55 277 | ❌ |

**Анализ.**

- **TC-C05** подтверждает: 500 ев/с превышает ёмкость 1 TM (~480 ев/с), events_per_sec=400 — Flink не успевает (lag растёт). p99=70 с — задержка накапливается из-за backpressure.

- **TC-C06** демонстрирует эффект горизонтального масштабирования после async-фикса: при удвоении числа TaskManagers и слотов (4→8) p99 упала с 70 с до **14 с** — SLA выполнен. Lag=128 — пайплайн работает в штатном режиме.

- **TC-C07** выявляет второй потолок производительности: при 900 ев/с общий throughput вставок в ClickHouse достигает максимума (~520 ев/с для одноузлового экземпляра), даже при async-сбросе и 8 параллельных писателях. Flink-слоты не перегружены (CPU), ограничение — пропускная способность записи ClickHouse.

**Итоговое заключение по §9.3.6.** Async-буферизация ClickHouse sink **подтверждает горизонтальное масштабирование Flink** при умеренной нагрузке: 2 TM (p=8) обрабатывают 500 ев/с в рамках SLA p99 ≤ 30 с, тогда как 1 TM (p=4) с той же нагрузкой нарушает SLA (p99 = 70 с). При нагрузке 900 ев/с bottleneck смещается на INSERT-пропускную способность одноузлового ClickHouse — для преодоления этого предела необходим кластер ClickHouse (см. §9.5.1, п. 3).

## 9.5 Оценка готовности к промышленной эксплуатации

Ниже приведена структурированная оценка по восьми стандартным критериям production-readiness (по методологии Google SRE / DORA).

| Критерий | Статус в прототипе | Что требуется для production |
|---|---|---|
| **Reliability** (RTO/RPO) | ✅ RTO 2 мин 37 с, RPO = 0 — измерено (TC-C03) | — |
| **Scalability** (горизонтальная) | ✅ После async-буферизации sink: 2 TM (p=8) обрабатывают 500 ев/с с p99 = 14 с (TC-C06). Потолок одноузлового ClickHouse ~520 ев/с INSERT-записи ограничивает нагрузку 900 ев/с (TC-C07). Архитектурно масштабируется горизонтально без изменений кода. | ClickHouse cluster (Distributed); стресс-тест при > 5 000 ев/с |
| **Observability** | ✅ Prometheus + Grafana + `alerts.yml`; метрики: e2e latency, consumer lag, DLQ rate, checkpoint duration | OpenTelemetry distributed tracing от источника до ClickHouse |
| **Data Durability** | ⚠️ Kafka: 1 broker, `replication.factor=1` | `replication.factor=3`, `min.insync.replicas=2` на ≥ 3-узловом кластере |
| **Exactly-once** | ✅ Effectively-exactly-once: L1 (Kafka idempotent) + L2 (Flink `MapState`) + L3 (`ReplacingMergeTree`) — верифицировано TC-A03, TC-B02 | — |
| **Security** (PII / TLS) | ⚠️ Токенизация `payer_id`/`payee_id` на стороне источника; TLS и auth не настроены в dev-среде | TLS между компонентами; маскирование в `ValidatorOperator`; RBAC в ClickHouse; соответствие 152-ФЗ/GDPR |
| **Schema Management** | ❌ JSON без Schema Registry; нет schema evolution и контроля совместимости | Avro + Schema Registry (BACKWARD compatibility); CI-автотесты совместимости схем |
| **Operability** | ✅ Runbook (`docs/runbook.md`); автоматические тесты (functional, DQ, load); воспроизводимое развёртывание | CI/CD pipeline; Kubernetes + Flink Operator для авто-скейлинга |

**Итог: 4/8 критериев полностью выполнены в прототипе; Scalability частично (⚠️).** Архитектурные решения (Kappa, stateful SCD2, трёхуровневая дедупликация) готовы к production. Горизонтальная масштабируемость *архитектурно* заложена, но ограничена производительностью ClickHouse sink при высокой нагрузке. Два инфраструктурных критерия (Data Durability, Security) и один процессный (Schema Management) требуют доработки.

### 9.5.1 Дорожная карта production-развёртывания

1. **Kafka cluster (≥ 3 брокеров):** `replication.factor=3`, `min.insync.replicas=2`; переход на KRaft mode (без ZooKeeper).

2. **Avro + Schema Registry:** переход с `SimpleStringSchema` (JSON) на Avro-десериализацию; BACKWARD-совместимость; аутентификация mTLS / Basic Auth.

3. **ClickHouse Cluster:** шардирование и репликация через `Distributed` таблицы; актуально при нагрузке > 5 000 ев/с.

4. **Late arrivals:** переход на native Flink Java/Kotlin (`ctx.timer_service()` поддерживается) или отдельный batch-job коррекции из топика `payments.late`.

5. **DLQ → ClickHouse:** дополнить `ClickHouseSink` маршрутизацией невалидных событий в таблицу `payment_dlq` для сквозной верификации.

6. **PII / Security:** маскирование в `ValidatorOperator`; TLS между Kafka–Flink–ClickHouse; RBAC; аудит доступа; соответствие 152-ФЗ.

## 9.7 Заключение

В ходе работы:

1. **Проведён сравнительный анализ** архитектурных паттернов (Lambda vs Kappa) и инструментов обработки потоков, обоснован выбор стека Kafka + Flink + ClickHouse.

2. **Спроектирована архитектура** NRT-пайплайна с гарантией effectively-exactly-once, трёхуровневой дедупликацией и гибридной моделью хранения (SCD Type 2 + append-only лог).

3. **Реализован рабочий прототип** — полностью функциональный код пайплайна (PyFlink DataStream API), генератор тестовых данных, мониторинг и автоматизированные тесты.

4. **Проведено тестирование:** 9/10 FR подтверждены тест-кейсами (TC-B07 late arrivals — xfail, Beam runtime). SLA p99 ≤ 30 с выполнен при нагрузке до **~480 событий/сек** (1 TaskManager, TC-C01). После перевода sink на async-буферизацию горизонтальное масштабирование **верифицировано**: 2 TM (parallelism=8) обрабатывают 500 ев/с с p99 = 14 с (TC-C06, SLA выполнен), тогда как 1 TM при той же нагрузке нарушал SLA (p99 = 70 с, TC-C05). Потолок производительности при 900 ев/с — INSERT-пропускная способность одноузлового ClickHouse (TC-C07). RPO = 0 подтверждён в тесте восстановления (TC-C03).

5. **Рассчитана ёмкость:** ~1.4 ТБ реальных данных за 3 года (с учётом сжатия LZ4).

6. **Проведена оценка production-readiness:** 4 из 8 критериев выполнены полностью (Reliability, Observability, Exactly-once, Operability); Scalability — частично (⚠️: горизонтальная масштабируемость архитектурно заложена, но ограничена sink-производительностью). Три критерия (Data Durability, Security, Schema Management) определены как roadmap до production-развёртывания (см. §9.5).

Разработанная система подтверждает ключевые требования прототипа (9/10 FR, SLA p99 при 500 ев/с на 2 TM, горизонтальное масштабирование верифицировано, RPO = 0) и может служить основой для production-развёртывания при реализации roadmap из §9.5.1. Выявленные ограничения (потолок INSERT-пропускной способности одноузлового ClickHouse при > 520 ев/с, отсутствие кластеризации и Schema Registry) определены как приоритетные задачи доработки.
